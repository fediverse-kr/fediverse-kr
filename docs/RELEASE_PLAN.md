# 소개 우선 릴리즈 — 마무리·분할개발 계획

2026-09-14. 상태: 사용자가 새 목표 실행을 승인했다. 입문 설명과 PG 워커 판정을 시작했다.
운영 배포는 승인된 유지보수자가 직접 수행한다. 구현 완료와 배포 준비 완료, 실제 배포 완료를 구분한다.
2026-09-15 작업 위치: 사용자 승인에 따라 WSL Ubuntu의 `<workspace>/fediversekr2`(ext4)를 기준 저장소로 사용한다.
Windows 원본은 `e0a543f` 체크포인트로 보존했다. WSL 빌드/검증은 Linux 경로에서 실행하며,
필요한 Windows 웹 빌드는 동일 소스 스냅샷을 사용하고 입력 해시를 대조한다.
사용자의 최신 우선순위는 새 소개를 갖춘 fediverse.kr를 빨리 공개하는 것이다.
기존의 누적 작업 문서는 증거로 보존하되, 거기 적힌 모든 개선 후보를 출시 조건으로 삼지 않는다.

## 출시 경계

첫 릴리즈는 **새 소개 + 기존 서비스의 안전한 인계**다. 모든 새 기획의 완성이 아니다.
Phoenix를 대체하는 기존 방향은 유지한다. 회원 기능을 없애거나 더미 데이터로 운영하지 않는다.
소개만 새 앱으로 보내고 회원/서버 기능은 Phoenix에 남기는 이중 운영을 기본안으로 추가하지 않는다.

| 첫 릴리즈에서 마칠 것 | 이후로 미룰 것 |
| --- | --- |
| 승인된 랜딩 유지, `/start`의 직관적인 스크롤 설명 마무리 | 랜딩 재디자인, 새 데모·설명 주제 확대 |
| 기존 전달·공개범위·거리두기 등 설명의 사실 오류/깨짐 수정 | 모든 상세 설명의 재기획·시각적 완성도 상향 |
| 실제 서버·소프트웨어 조회와 기존 회원/소유권/댓글/숨김/이미지 보존 | 사람 찾기, 공개 프로필, 운영·개발 위키, 분류 정책 확대 |
| 이미 연결된 로그인·회원·관리 동선의 필수 회귀 확인 | 인증 방식 재설계, 계정 연동의 추가 편의 기능 |
| 현재 수집/정리 작업의 실행·복구 확인 | 워커 대시보드 확장, 범용 큐/actor 플랫폼 개발 |
| 한 운영 대상의 배포·실자료 이관·전환/복귀 확인 | 배포 플랫폼 확대, 다중 저장소 backend, 새 관리 도구 |

이미 구현된 추가 기능은 삭제하거나 새로 다듬지 않는다. 단, 공개되는 쓰기 API의 권한·정보 노출
문제는 선택 기능이어도 출시 차단이다. 미완료 기능을 보류할 경우 메뉴만 감추고 API를 열어두지 않는다.
보류를 위해 범용 feature-flag 시스템을 새로 만들지도 않는다.

## 워커 결정: 현재 PG를 판정하고, 통과하면 끝낸다

현재 구현은 Diesel 기반 PG 큐이며 작업 점유·만료 회수·중복 결과 차단과 재시작 검증 기록이 있다.
이는 새로 큐를 개발해야 한다는 뜻도, 현재 운영 환경에서 검증을 끝냈다는 뜻도 아니다.

1. 기존 테스트/실행 도구로 아래 조건을 한 번 판정한다.
2. 결함이 국소적이면 한 차례 묶어서 수정하고 실패 영역을 재검증한다.
3. 큐 핵심 구조를 다시 설계해야 한다면 그 작업을 계속 늘리지 않고 NATS JetStream 대안으로 전환 비용을 판정한다.
4. PG가 통과하면 이번 릴리즈에는 그대로 고정한다. Kameo 추가는 출시 조건이 아니다.

판정 조건:

- 정기 수집과 기존 수동 갱신이 실행되고 관측 결과가 저장된다.
- 프로세스 중단 후 미완료 작업이 회수된다. 늦은 결과/중복 실행이 데이터를 덮지 않는다.
- 원격 서버 실패와 실행기 장애가 구분되고, 재시도가 무한/고속 반복되지 않는다.
- 종료한 서버·숨긴 서버·운영자 편집 내용의 기존 정책이 보존된다.
- DB 일시 장애 후 복구하며, 종료 제한을 지킨다.
- 실제 대상 수에 맞춘 한 주기의 처리량, HTTP 영향, 메모리/DB 연결 사용을 측정한다.

범용 supervisor/큐를 도메인 규칙이라고 포괄적으로 정당화하지 않는다. 다만 유지보수 개선만을
위한 교체를 긴급 출시의 필수 경로로 새로 넣지도 않는다.

### PG의 구조 수정이 필요할 때만: NATS JetStream

- 애플리케이션과 크롤러는 계속 같은 바이너리/프로세스. 별도 워커 컨테이너는 만들지 않는다.
- JetStream 서버와 영속 볼륨은 별도 자원이 필요하다. 가용 CPU/RAM/디스크와 기존 NATS 유무를 확인한다.
- 파일 저장, durable pull consumer, 처리 완료 후 ack를 후보로 삼는다. 저장량·보류 작업·동시 처리에 상한을 둔다.
- 저장소 상한은 프로세스 전체 메모리 상한이 아니다. 실제 소비량과 컨테이너 제한을 함께 확인한다.
- 무조건 3대 복제부터 구성하지 않는다. 단일 구성은 HA가 아니므로 장애 허용·복구 조건을 별도 합의한다.
- DB 반영과 큐 처리 확인 사이의 장애·중복에 대한 안전성은 앱에 남는다. 브로커 도입만으로 해결됐다고 하지 않는다.
- PG 큐와 NATS 큐를 함께 장기 운영하거나 두 backend를 지원하는 범용 추상화를 만들지 않는다.
- 전환 시 현재 예약/실행 중 작업의 배출·재예약 경로와 기존 수집 정책도 인계한다.
- 선택 버전/클라이언트 의존성의 라이선스를 확인한다. GPL 계통 소스를 사용하지 않는다.

공식 근거: [JetStream 설정](https://docs.nats.io/reference/config/jetstream/),
[pull consumer](https://docs.nats.io/learn/jetstream/pull-consumers).
이는 후보 설계이지 클러스터 자원 검증이나 설치 승인이 아니다.

## 분할개발 패킷

최대 두 구현 작업만 병행한다. UI 담당자는 명확한 UI·문서·배포 설정을 담당하고,
백엔드 담당자는 데이터·인증·워커 판단과 UI 담당자 변경의 검토를 담당한다. 통합 담당자는 범위·충돌·최종 판정에 집중한다.
소개와 워커 판정부터 배정했다. 나머지는 선행 패킷의 종료 조건을 확인한 뒤 배정한다.

| 순서/패킷 | 담당 | 변경 경계와 산출물 | 종료 조건 |
| --- | --- | --- | --- |
| 0. 기준선 고정 | UI 담당자 → 백엔드 담당자 확인 | 현재 소스/lock/자산의 체크포인트 준비, 비공개 자료 제외, 출시 차단 목록 | 기존 결과와 미검증을 분리한 한 목록. 무관한 정리/리팩터링 없음 |
| A. 소개 출시본 | UI 담당자 → 백엔드 담당자 검토 | `src/explainer/`, 설명 전용 CSS/스크롤 코드. 공통 데모 변경은 별도 표시 | `/start`에서 익숙한 SNS → 다른 서버 사람이라는 발견 → 주소/개인 공간 연결이 짧은 문구와 화면으로 이어짐. PC/모바일 검토 묶음 |
| B. 회원·실자료 인계 | 백엔드 담당자 | 기존 importer/activation/회원·미디어 경로 재사용. 발견한 이관 결함만 수정 | 실제 사본의 ID·관계·권한·숨김·원본 값/파일 대조, 기존 회원 로그인 확인. 합성 결과로 대체하지 않음 |
| C. 수집 출시 판정 | 백엔드 담당자 | `backend/runtime.rs`, 기존 수집/큐 저장소와 해당 테스트만 | 위 PG 판정 통과 또는 구조 결함·JetStream 전환 비용/자원 요구의 명확한 결론. 대시보드 추가 없음 |
| D. 배포 후보 준비 | UI 담당자 → 백엔드 담당자 검토 | 기존 `deploy/`와 배포 도구 재사용, 실제 대상 설정/경로/복귀 절차 | 한 Linux 대상의 서버·WASM·자산이 일치하는 실행 묶음과 환경 입력 목록. 브로커는 C의 결정 전 추가하지 않음 |
| E. 통합·최종 인수 | 백엔드 담당자 검증, 통합 담당자 판정 | 위 결과를 고정한 배포 후보 한 개 | 소개 검토, 실제 HTTPS/AP·로그인·서버 조회·수집·이미지, 최종 사본 이관과 전환/복귀 조건 통과 |

실행 순서:

- 0 다음 A와 C를 병행한다. 이때 배포/실자료에 필요한 입력 목록을 한 번에 전달한다.
- C가 닫히면 B를 진행한다. 실자료 입력이 준비되지 않았다면 D의 준비만 진행하고 B는 미검증으로 남긴다.
- A가 닫히면 D를 진행할 수 있다. B와 D는 충돌 없는 파일 경계를 지키며 병행한다.
- A~D 결과가 모이면 E. 선택 개선을 발견해도 새 패킷을 자동으로 시작하지 않는다.
- B의 외부 입력 대기 중 다른 필수 패킷까지 닫혔다면 종료하고 입력을 기다린다. 추가 기능으로 시간을 채우지 않는다.

## 소개 패킷의 판단 기준

랜딩은 pass 상태를 유지한다. 처음 보는 사람이 설명의 긴 글을 읽기 전에
“같은 곳에서 대화하는 줄 알았는데 각자 다른 사이트에 있다”를 화면에서 알아볼 수 있어야 한다.
이메일/개인 홈페이지 비유와 연합우주라는 이름은 이 발견을 정리하는 짧은 문장으로 사용한다.
현재 제품 모티프와 랜딩 공통 컴포넌트를 유지하고, 전달을 날아가는 방향으로 표현하지 않는다.
입문은 집중적으로 마무리하되 나머지 이미 있는 주제는 정확성·스크롤/모바일 동작만 확인한다.
문구 변경량, 테스트 개수로 설명의 설득력이 좋아졌다고 판정하지 않는다.
사용자에게는 입문 PC/모바일과 세부 설명 대표 장면을 한 묶음으로 보여준다.

## 사용량·검증 상한

- 각 패킷은 지정 산출물로 끝낸다. 담당자에게 목표 전체를 떠넘겨 추가 과제를 찾게 하지 않는다.
- 기본은 구현 1회 + 검토 1회 + 지적 수정 1회. 그 뒤에도 구조 문제가 남으면 범위/대안 보고로 끝낸다.
- C의 첫 판정은 30분을 목표로 하고, 빌드 대기와 실제 작업을 구분해 기록한다. 이를 넘겨 재설계에 들어가지 않는다.
- 일상적인 UI·문서·반복 확인을 통합 담당자가 중복 수행하지 않는다. 추가 검토는 특정 통합 난제에 한정한다.
- 패킷별로 변경 영역의 집중 테스트만 실행한다. Cargo/Dioxus 빌드는 한 번에 하나만 실행한다.
- 운영 대상의 전체 회귀/배포 검증은 통합 후보에서 실행한다. 변경할 때마다 Windows와 Linux 전수를 반복하지 않는다.
- 후보 검증 뒤 코드를 바꾸면 영향 영역과 필요한 통합 검증을 다시 실행한다. 실패를 무시하거나 검증하지 않은 수정본을 출시하지 않는다.
- 기존 이관/보안 검사와 도구를 재사용한다. 원본 회원 정보/키/사진을 로그·문서·커밋·이미지에 포함하지 않는다.
- 보고는 패킷 완료/실패/입력 대기와 남은 출시 차단만 적는다. 주관적 전체 퍼센트와 누적 테스트 수를 진척 대신 사용하지 않는다.
- 선택 과제의 자동 추가·무기한 개선·사용량 리셋을 전제로 한 계획은 만들지 않는다. 사용자의 새 목표 승인 범위에서만 진행한다.
- 작업 예산은 운영자가 확인하고 필요시 중단한다. 추가 작업이 필요하면 범위와 비용을 먼저 확인한다.

## 한 번에 모을 외부 입력과 실제 전환 경계

- 암호화 DB 백업의 로컬 복호화 수단. 암호를 채팅이나 명령행에 기록하지 않는다.
- 기존 이미지 저장소의 실제 파일 보관본/접근 경로. DB의 키만으로 파일 이전을 완료 처리하지 않는다.
- 운영 대상 아키텍처, PG/TLS, 미디어 볼륨, 공개 HTTPS/프록시, CPU/RAM/디스크 여유.
- 실제 AP 인증에 참여할 계정과 운영 관리자 지정, 유지보수/전환 창.

현재 실자료 복원·실회원 인증·운영 전환을 완료했다는 증거는 없다.
실자료 리허설에는 제공된 백업을 사용하고, 실제 전환 때에는 최신 사본으로 같은 절차를 반복한다.
전환 직전 쓰기를 멈추고 최종 백업/대조 후 트래픽을 옮긴다. 새 서비스의 쓰기를 연 뒤
되돌리는 경우 새 쓰기를 먼저 차단·보존해야 하며, 예전 이미지로만 되돌려 데이터가 보존된다고 하지 않는다.
자동 양방향 DB 변환기를 새로 만들지 않는다. 복귀 시 쓰기 보존·수동 복구 범위를 운영자가 이해하고 승인해야 한다.
운영 배포·실제 계정 게시·Phoenix 종료는 별도의 명시적 실행 승인 없이 하지 않는다.

만일 필수 인계만으로도 첫 공개가 계속 막히면, **소개만 먼저 부분 공개하고 Phoenix를 일시 유지하는 안**을
별도 선택지로 보고한다. 이 경우 라우팅/로그인 동선과 두 앱의 일시 자원이 필요하며, 지금 기본안으로 구현하지 않는다.
