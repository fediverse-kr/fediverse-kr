# 관리자 권한 · 신고 처리

후속: [사이트 관리자](site-moderation.md)를 같은 역할·메뉴에 연결했다. 일반/강제 숨김·종료·초대제·태그와 PG 수동 수집은 구현했으며, 물리적 삭제·소프트웨어 관리·운영 관리자 지정은 별도다. 아래 신고 처리 단위의 범위와 구별한다.

2026-09-14. Phoenix MIT 소스의 `Moderation`, `Report`, `Accounts.admin?`,
`AdminLive`를 확인해 신고 관리 흐름을 연결했다. 기존 관리자 화면 전체를
포팅했다는 뜻은 아니다. [MIT 고지](../licenses/phoenix-reference.MIT.txt).

## 권한과 운영자 명령

Phoenix는 설정의 `ADMIN_HANDLES`를 정규화한 회원 주소와 비교했다. 새 버전은
여러 AP 계정 및 자체 로그인을 갖는 **내부 회원 UUID**에 권한을 부여한다.
다른 SNS 계정을 연결하거나 표시 이름을 바꾸는 것으로 권한이 생기지 않는다.
첫 가입자 자동 관리자, 공개 권한 부여 API, 개발용 인증 우회 endpoint는 없다.

같은 애플리케이션 바이너리를 사용하는 명시적 호스트 운영자 명령:

```text
fediversekr2 --admin grant <member-uuid>
fediversekr2 --admin revoke <member-uuid>
```

`FEDKR_DATABASE_URL`, `FEDKR_PUBLIC_ORIGIN`의 설정 검사를 재사용한다. 마이그레이션을
적용하고 지정한 기존 회원의 권한만 바꾸며 HTTP·워커·AP 조회·키 생성은 시작하지
않는다. 원본/격리 이관 DB는 차단한다. 중복 실행은 변경·이력을 추가하지 않는다.
차단된 회원에 대한 grant는 거절한다. 입력 UUID만으로 회원을 만들지 않는다.

**기존 관리자 설정은 DB 덤프에 없다.** 실제 전환 때 기존 `ADMIN_HANDLES`와
이관한 회원을 확인하고 UUID를 명시적으로 지정해야 한다. 추측한 계정이나
실회원에는 권한을 부여하지 않았다. 검토 사본의 [명시적 활성화](activation.md)는 구현했지만
실제 자료의 활성화/운영 전환은 하지 않았다.

## 화면과 조치

- `/account`에서 실제 관리자에게만 신고 관리 링크를 표시한다.
- `/account/moderation`: 상태별 목록, 최신순 20개씩. 추천·자동 판정 없음.
- `/account/moderation/profiles`: [전체 회원 사진·이모지 갱신](profile-media-refresh.md).
  개인 정보 설정은 유지하며 웹과 같은 프로세스의 PG 작업으로 처리한다.
- `/account/moderation/:id`: 신고 설명, **신고 당시 원문**과 **현재 댓글**을 분리한다.
  옛 신고에 원문 snapshot이 없으면 없다고 표시한다. 삭제된 댓글도 관리자는
  보존 원문을 볼 수 있다. 원격 HTML과 메모는 텍스트이며 실행하지 않는다.
- 신고 처리 완료·기각·다시 검토, 댓글 삭제 표시, 작성자 이용 차단·해제는 별도
  조치다. 신고 완료가 자동 삭제/차단을 뜻하지 않으며 그 반대도 마찬가지다.
- 적용 전에 조치 설명과 1~1,000자 사유를 확인한다. 저장 실패 시 초안을 남기고,
  충돌 후에는 명시적으로 최신 내용을 불러와 다시 조치를 선택해야 한다.
- 댓글·신고 revision과 회원 변경 시각을 비교한다. 차단→해제 뒤 과거 차단 요청을
  다시 보내도 허용하지 않는다. 타인의 동시 편집/판정을 덮어쓰지 않는다.
- 이용 차단은 fediverse.kr에만 적용한다. 모든 세션과 연결 계정/기존 회원 주소의
  대기 인증 요청을 폐기한다. 차단 해제 후 예전 쿠키가 되살아나지 않는다.
- 관리자 본인과 다른 관리자 계정의 이용 차단은 거절한다. 필요하면 호스트 운영자가
  먼저 해당 역할을 회수해야 한다. 공개 댓글 삭제는 기존 답글과 신고를 보존한다.
- `/admin`, `/admin/reports` GET/HEAD는 새 신고 목록으로 308 이동한다.
  옛 관리 query를 전달하지 않는다. 서버 관리도 같은 메뉴로 연결했고 소프트웨어 관리 탭은 남았다.

## 보안 · 저장 경계

`moderation` DTO/화면/API → `backend/moderation` 입력 계약 →
`backend/db/moderation` Diesel/PG. DB 연결/SQL을 UI로 노출하지 않는다.
신고 및 이력 조회는 매번 현재 세션·차단 상태·관리 권한을 재검사한다. 조치는
추가로 15분 이내 재인증을 요구한다. private/no-store/Vary Cookie, Origin,
실제 본문 8 KiB 상한은 기존 회원 HTTP 경계를 재사용한다.

관리 쓰기는 PG advisory gate로 직렬화한다. 잠금 순서는 gate → 조치자/세션 →
필요 시 비관리자 대상 회원 → 서버 → 댓글 → 신고다. 기존 댓글/탈퇴 순서와
일치시킨다. 감사 기록의 대상 UUID에는 FK를 두지 않아 댓글을 잠근 뒤 다른
회원 잠금을 역순으로 요구하지 않는다. 댓글 변경 알림은 commit 뒤에만 보낸다.

Migration 014는 역할, 비공개 조치 이력, 신고 목록 인덱스를 추가한다. 이력에는
조치자, 대상, 이전/이후 상태, 사유, 시각만 저장한다. 연동 주소·암호·원문 전체를
다시 복제하지 않는다. 탈퇴한 조치자의 회원 FK는 NULL로 분리하고 행은 보존한다.
대상 UUID와 신고 시점 원문/이름은 비공개 보존되므로 완전한 개인정보 삭제로
안내하면 안 된다. **보관 기간 및 조회 감사 정책은 아직 운영 검토 사항**이다.

이력은 20개씩, 페이지 입력은 최대 10,000이다. 기존 신고 설명/메모가 1,000자를
넘으면 원본은 유지하고 UI에 생략 여부를 표시한다. 댓글은 importer 계약의
최대 1 MiB를 읽으며 화면 안에서 스크롤한다. 신고 증거는 기존 1 MiB 제약을 따른다.

역할/이력이 있는 migration의 rollback은 거절한다. importer는 새 두 테이블을
계약에 포함하고, 격리 대상에 역할이나 이력이 생겼으면 재이관으로 지우지 않고
거절한다. 실데이터의 권한 이관/서비스 활성화를 대신하는 우회는 아니다.

## 검증과 남은 범위

- 실제 격리 PG: 역할 검증·회수, 세션/ban/freshness, 동시 판정, 댓글 충돌,
  증거 보존, 삭제·신고 상태 분리, 세션/익명 proof 폐기, 차단 상태 왕복 충돌,
  숨김 서버 신고 조회, 탈퇴 후 FK 분리, 입력/이력 페이지 상한.
- 합성 Phoenix 이관 후 역할/이력 주입을 감지해 재이관과 runtime을 거절한다.
- `check-moderation-browser.js`: 실제 HTTP/PG로 40개 검사. 응답 mock 없음.
  1440/390/320px, 직접 캡처 검토 후 모바일 버튼 폭과 시각 표기를 정리했다.
- `check-moderation-role.ps1`: 같은 바이너리의 revoke/grant/중복 grant,
  일반 회원으로 강등된 세션의 API/SSR/쓰기 거절. 가상 회원만 사용한다.

물리적 서버 삭제, 소프트웨어 잠금/분류/로고 관리, 신고와
무관한 회원 검색·제재 목록은 아직 남아 있다. 이 단위를 관리자 전체 parity나
실제 운영 검증으로 간주하지 않는다. 최신 실행 수치는 [통합 기록](integration-checks.md).
